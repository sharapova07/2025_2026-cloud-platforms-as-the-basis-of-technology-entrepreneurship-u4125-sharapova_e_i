## "Разработка инфраструктуры MVP AI приложения.Разработка инфраструктуры MVP AI приложения"

### Ход работы   
**1. Описание приложения:**  
Суть приложения: сервис для транскрибации аудио в текст.  
AI-модуль: распознавание речи и преобразование аудиофайлов в текст с помощью Google Cloud Speech-to-Text.    
Сценарий работы приложения: пользователь загружает аудиофайл, приложение сохраняет его в облачное хранилище, отправляет на распознавание речи и возвращает пользователю готовую текстовую расшифровку.  

Функциональные модули:  
| Модуль | Frontend | Backend |
|---|---|---|
| Стартовая страница | ✓ | ✓ |
| Форма загрузки аудио | ✓ | ✓ |
| Личный кабинет | ✓ | ✓ |
| История транскрибаций | ✓ | ✓ |
| Хранение аудиофайлов | — | ✓ |
| Запуск транскрибации | — | ✓ |
| Отображение статуса обработки | ✓ | ✓ |
| Просмотр готового текста | ✓ | ✓ |
| Скачивание результата | ✓ | ✓ |
| Мониторинг / Логирование | — | ✓ |

- Состояние 3 (продакшн) - до 100 000 пользователей

**2. Состояни 1 - начальное (MVP):**  
Цель: быстро и недорого запустить рабочий прототип, а также проверить основную гипотезу, что пользователи готовы загружать аудио и получать текстовую расшифровку.  
Выбранная стратегия: простое serverless-приложение без сложной очереди и микросервисов. Backend принимает файл, сохраняет его в хранилище и отправляет на распознавание.

**4. Состояние 3 - продакшн:**

**Дополнительный вариант обработки**   
Для транскрибации можно использовать не только Standard Recognition, но и Dynamic Batch Recognition. Этот режим дешевле, но подходит для задач, где результат не нужен мгновенно    
| Стадия | Минут аудио/мес | Standard Recognition, $0.016/мин | Dynamic Batch, $0.003/мин |
|---|---:|---:|---:|
| MVP | 1 000 | ~$16 | ~$3 |
| Тестирование партнёрами | 15 000 | ~$240 | ~$45 |
| Продакшн | 200 000 | ~$3 200 | ~$600 |  

В основной экономической модели используется Standard Recognition, потому что он лучше подходит для сценария, где пользователь ожидает получить результат быстрее. Dynamic Batch можно использовать как более дешевый режим для отложенной транскрибации

**6. Обоснование выбора ресурсов:** 
1. Cloud Run выбран для всех стадий, потому что приложение имеет непостоянную нагрузку. Serverless-подход позволяет не содержать серверы постоянно и платить за фактическое использование;
2. Cloud Storage используется для хранения аудиофайлов и текстовых результатов. Хранить большие файлы в базе данных нецелесообразно, поэтому база содержит только статусы и ссылки;
3. Firestore выбран для хранения метаданных: пользователей, статусов задач, ссылок на файлы и результатов транскрибации. Для MVP этого достаточно, так как не требуется сложная реляционная модель;
4. Pub/Sub добавляется со второй стадии, потому что обработка аудио может занимать длительное время. Очередь позволяет не блокировать пользователя и обрабатывать задачи асинхронно;
5. Speech-to-Text API выбран как основной AI-компонент. Для студенческого MVP нецелесообразно обучать и разворачивать собственную ML-модель, так как это потребует отдельной ML-инфраструктуры и дополнительных затрат;
6. Secret Manager используется на продовой стадии для безопасного хранения секретов и переменных окружения;
7. Cloud Scheduler нужен для автоматической очистки старых аудиофайлов, чтобы не увеличивать стоимость хранения.

## Вывод

В ходе работы была спроектирована инфраструктура AI-приложения для транскрибации аудио в текст. Для реализации выбран стек сервисов Google Cloud: Cloud Run, Cloud Storage, Firestore, Pub/Sub и Speech-to-Text API.

На первой стадии приложение запускается как простой MVP с минимальными расходами около $16–17 в месяц. На второй стадии добавляется очередь задач и отдельный worker, что повышает стабильность при тестировании партнерами. На третьей стадии инфраструктура усиливается за счет разделения сервисов, мониторинга, Secret Manager и автоматической очистки файлов.

Главный вывод: для приложения транскрибации основная стоимость формируется не backend-инфраструктурой, а количеством минут аудио, обработанных через Speech-to-Text. Поэтому при росте продукта важно заранее учитывать себестоимость одной минуты транскрибации и при необходимости использовать более дешевый режим Dynamic Batch для отложенной обработки.
